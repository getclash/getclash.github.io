系统代理和 TUN 有什么区别：从流量入口理解

用流量入口、权限、DNS 和规则四个角度比较系统代理与 TUN，找到浏览器能用而某个应用不能用的原因。

Clash 图鉴编辑 7 分钟更新于 2026.10.27

系统代理和 TUN 解决的是“流量怎样进入内核”。规则模式和全局模式解决的是“进入后走哪个出口”。把这两层分开理解，才能解释为什么开启 TUN 后，部分流量仍然按规则直连。

01系统代理：让遵循设置的应用主动转发

桌面客户端打开系统代理时，会修改操作系统的代理设置，指向本地监听端口。遵循该设置的应用将请求交给内核；自行实现网络栈、使用独立代理配置或忽略系统设置的程序，可能不会经过这个入口。

浏览器可以使用而命令行工具不行，不能直接判断订阅失效。先查看工具的代理选项与环境变量支持，并在客户端连接记录里确认请求是否出现。具体端口以当前客户端显示为准，不要照搬网上的固定数值。

02TUN：在网络层接管一部分或更多流量

TUN 使用虚拟网络接口与路由把数据交给内核，适合需要处理不遵循系统代理的应用。桌面系统通常需要相应权限或辅助服务。能接管哪些地址与协议，还受路由、排除列表、协议栈和平台实现影响。

因此“TUN 已开启”不能等同于“全部网络都走远端节点”。局域网、排除应用和直连规则仍可能存在。Android 的客户端常借助系统 VPN 接口实现接管，设置方式也不应直接照搬 Windows。

03规则与全局是另一层选择

请求进入内核后，规则模式按照配置中的规则决定出口；全局模式使用指定的全局策略。即使叫“全局”，也不意味着忽略该软件的接管边界，或让一个从未进入内核的应用自动受控。

  • 浏览器使用正常、某应用无记录：优先排查流量入口。
  • 连接有记录但走错出口：优先检查命中规则与策略组选择。
  • 所有请求都连接失败：检查节点本身、认证、DNS 与网络。
  • 只有局域网服务异常：检查路由、直连规则和 TUN 排除设置。

04DNS 与其他 VPN 是常见变量

TUN 配置可能包含 DNS 接管，但不是所有 DNS 流量都会自动交给内核。应用自带的加密 DNS、特定路由和平台限制，都会改变请求路径。先查看内核 DNS 日志，再决定是否需要调整设置。

同时开启多个 VPN、虚拟网卡和自动改写代理的工具，会使路由与代理状态难以判断。先只保留一个接管工具复现问题，记录原设置；不要一次修改 MTU、IPv6、DNS 和全部路由。

05用最小变更确定适合的方式

主要使用遵循系统代理的桌面应用时，可以先从系统代理开始。确实需要其他应用、特定 UDP 流量或统一路由时，再阅读项目的 TUN 文档。以可观察的连接结果判断，而不是把 TUN 当作提速按钮。

  1. 保存当前设置，先验证系统代理下的基础连接。
  2. 关闭其他接管工具，按官方指引启用 TUN。
  3. 检查目标应用、局域网和 DNS，再与原结果比较。
  4. 关闭 TUN 并退出，确认网络恢复；不符合需求时回到上一状态。

常见问题

TUN 一定比系统代理快吗？+

不一定。它改变流量入口和接管范围，不直接改善服务器线路。性能还受内核、协议、网络和设备负载影响。

开启 TUN 后还需要开系统代理吗？+

取决于客户端实现和你的应用需求。先按项目官方建议使用一种已验证方式，不必为了“更全面”盲目同时开启所有开关。
