旧 Clash 客户端迁移：保留配置，分阶段替换

为 Clash for Windows、早期 ClashX 等旧客户端制定迁移顺序，备份订阅与规则，验证 Mihomo 兼容性并清理残留代理。

迁移的重点不是把旧目录全部复制过去，而是保留可恢复的资料、确认配置兼容，再切换系统接管。历史客户端可以留作资料参考，但不要因为名字熟悉，就假设新的系统和协议仍与它兼容。

01先列出需要保留的内容

记录旧客户端版本、正在使用的订阅、策略组选择、局域网例外、自定义规则和端口。区分“配置提供者下发的原始内容”与“旧客户端生成或覆盖的内容”，迁移时往往只需要前者加上必要的个性化设置。

使用客户端自己的导出方式备份可用配置，另存重要自定义内容。备份可能含有密码和订阅令牌，应保存在私人位置。确认备份能读取后，再考虑卸载；不要把整个数据目录传到公共仓库求助。

02按功能需求选择目标项目

先看目标客户端的平台、系统要求和维护状态，再核对订阅使用的协议与字段。Mihomo 与历史 Clash 内核有继承关系，但这不代表所有脚本、界面偏好、旧版私有字段都可以无修改迁移。

桌面可以比较 Clash Verge Rev、FlClash；Android 可以根据设备和配置需求比较相应客户端。旧客户端停更、仓库失效和原发布附件不可用是不同状态，阅读原项目公告比依赖转载站的“最新版”标签更可靠。

03先并存验证，避免同时接管

安装新客户端时，暂时保留旧版作为回退。两个应用可以先同时存在于磁盘，但验证网络时只允许一个修改系统代理或启用 TUN。否则出现连接异常，很难确定是哪一个应用的路由和监听端口正在生效。

  1. 在旧客户端关闭系统代理、TUN 和开机启动，再正常退出。
  2. 新客户端先导入原始订阅或配置副本，不迁入全部旧缓存。
  3. 确认配置可加载、策略组和节点存在，先验证基础系统代理。
  4. 逐项迁移自定义规则，每改一项就用连接记录检查实际结果。

04按使用场景验收，而不是只测延迟

列出日常真正依赖的场景：浏览器、命令行、公司内网、家庭 NAS、音视频和必要的 UDP 应用。逐项检查是否进入内核、命中哪条规则、是否选择预期出口，再判断是否需要 TUN。

只要延迟数字看起来正常就卸载旧版，可能漏掉局域网与退出恢复问题。新客户端能够正常关闭、重启后没有重复启动项、代理设置可以恢复，同样属于迁移完成的条件。

05确认可回退后再清理旧环境

持续使用并确认关键场景正常后，再按原项目说明卸载旧客户端与专属辅助服务。不要手动删除所有虚拟网卡或不认识的系统服务，它们可能属于别的软件。保留一份必要配置和版本记录即可。

若迁移失败，先关闭新客户端的代理与 TUN，再恢复旧客户端原设置；不要让两者争用同一端口。根据错误阶段查配置兼容、服务权限或 DNS，必要时使用脱敏日志向目标项目反馈。

常见问题

可以直接复制旧客户端整个配置目录吗？+

不建议作为首选。目录可能包含旧内核、缓存、绝对路径和应用专属设置。优先导出配置与自定义规则，再按新客户端文档迁移。

迁移后需要重新购买订阅吗？+

更换客户端本身通常不等于更换服务。先确认现有订阅是否提供目标内核兼容格式及所需协议；本站不提供或销售订阅。
