Clash DNS 排查：从域名解析到连接记录

按解析、入口、节点域名和分流四个阶段定位 Clash 与 Mihomo DNS 问题，理解 fake-ip，避免一次改动整份配置。

Clash 图鉴编辑 9 分钟更新于 2026.10.27

网站打不开可能发生在解析、路由、握手或应用层。先保留一条可复现的错误，再判断是不是 DNS。随意替换一组公共 DNS 可能掩盖问题，也可能让局域网域名和节点解析更复杂。

01先建立可比较的测试条件

记录目标域名、发生时间、网络类型、客户端和内核版本，以及是否启用 TUN。选择一个稳定可访问的普通网站作对照，在同一网络下分别检查客户端开启和关闭时的结果。不要同时更新订阅或替换节点。

打开日志，区分“无法解析域名”“连接服务器超时”“TLS 握手失败”等错误。只凭浏览器一张错误页，通常不足以确定 DNS。原始日志可能包含私人域名和服务器信息，分享时先做必要脱敏。

02确认到底由谁解析

操作系统 DNS、浏览器安全 DNS、应用自己的解析器和 Mihomo 内置 DNS 可以同时存在。系统代理下某些域名可能交由代理端处理；TUN 下也要看 DNS 接管和路由是否生效。普通 nslookup 的结果不一定代表浏览器实际路径。

先看目标请求是否进入连接记录，再看内核是否记录相应域名解析。若应用完全无记录，优先排查接管方式；若只有某个浏览器异常，临时检查该浏览器的独立 DNS 设置并记录原值，测试后恢复。

03看到 fake-ip，不要直接当成错误地址

在 fake-ip 模式中，内核可以为域名返回用于映射的地址，随后把实际连接关联回域名。这类地址的出现不自动意味着 DNS 污染。是否正常，应结合内核模式、映射和最终连接日志判断。

局域网主机、打印机或某些特殊应用可能需要真实解析结果。遇到此类兼容问题，先确认具体域名，再了解 fake-ip-filter 和 nameserver-policy 的用途；不要一遇到异常就把所有域名加入排除。

04别把节点解析和目标网站解析混为一谈

即使目标网站可以解析，代理节点的服务器域名无法解析也会导致连接失败。Mihomo 的 proxy-server-nameserver 专门影响节点域名的解析；这与普通 nameserver、直连解析和按域名指定解析服务器是不同环节。

如果 DNS 查询本身需要经过尚未建立的代理，可能出现先有连接还是先有解析的依赖问题。按官方文档检查解析链，保留可直接工作的基础解析路径，不应通过关闭 TLS 证书验证来掩盖解析或连接错误。

05每次只改一项，并保留回退

先备份生效配置，确认客户端是否会覆盖 DNS 字段，再测试最小修改。Wi-Fi、移动网络和公司内网的 DNS 条件不同，一套配置不能仅凭一次测试就称为通用最优。

  1. 确认当前配置可激活，目标请求进入内核。
  2. 检查节点服务器域名能否解析，再检查目标域名解析日志。
  3. 按实际场景核对 DNS 上游、策略和 fake-ip 例外，逐项修改。
  4. 必要时通过客户端提供的方式清理相关缓存，避免把旧结果当新结果。
  5. 测试普通网站、目标站点和局域网服务；无改善就恢复原设置并保留对照记录。

常见问题

换成加密 DNS 就一定能解决问题吗？+

不一定。加密 DNS 改变查询传输方式，仍需保证解析服务器可达、节点域名有正确的解析路径，并与路由策略配合。

fake-ip 地址说明网站真实 IP 被改了吗？+

不一定。fake-ip 是内核用于关联域名与连接的机制；应查看当前 DNS 模式和实际连接记录，不能只看解析结果判断故障。
